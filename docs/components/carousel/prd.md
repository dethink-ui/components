# Carousel PRD

## Problem Statement

Teams building media showcases, feature highlights, and marketing sections with Dethink Components have no carousel primitive. The library ships CardScroller (a selectable scroll-snap row) and CardStack (a single active deck), but neither delivers the browse-a-gallery interaction consumers expect from a carousel: a strip of items with a clearly featured center item, previous/next controls, position dots, and momentum drag. When teams reach for a third-party carousel they inherit an Embla/Swiper-style flat slider that looks like every other 2010s carousel, ignores the design system's tokens, density, RTL, and reduced-motion contract, and hydrates nondeterministically under SSR. Nothing in the ecosystem offers a carousel that reads as _physical objects standing on a receding floor_ — gallery frames or record sleeves with depth, contact shadows, and inertia — while still being a fully accessible, generic-children component.

## Solution

Ship **Carousel**, a Motion-powered compound component with three staging variants selected by a single `staging` prop:

- `flat` — a conventional centered slider with no 3D, the safe default for dashboards and dense UIs.
- `tilt` — cards rotate and recede slightly toward the edges (a restrained perspective row).
- `floor` — the hero look: cards stand upright on a receding floor with shared vanishing point, contact shadows, depth push-back, and subtle depth blur.

The whole visual system is driven by **one number**. A single `offset` MotionValue (a float in index units, `0…count−1`) is written to a `--carousel-offset` CSS custom property on the root. Every item carries its own `--carousel-item-index`, and every per-card transform (horizontal position, rotateY, translateZ, scale, blur, contact-shadow size/opacity) is a pure CSS `calc()` of `--carousel-distance: calc(var(--carousel-item-index) - var(--carousel-offset))`. Motion's only job is the physics on that one number: pointer-drag tracking, velocity-projected snap, and a spring settle. This keeps the repo rule "CSS transforms first, Motion for JS-driven animation only," makes SSR render the correct resting pose with zero JS (the server inlines `--carousel-offset`), turns reduced motion into "zero the 3D tokens and jump instead of spring," and makes `flat` staging simply the case where the 3D rules do not match.

The public API is a shadcn-name-compatible compound component wired through React Context: `Carousel`, `CarouselContent`, `CarouselItem`, `CarouselPrevious`, `CarouselNext`, `CarouselDots`, and a `useCarousel()` hook. It is independently installable from the registry, SSR-deterministic, reduced-motion aware, RTL-aware, density-aware, and theme-adaptive in light and dark mode. Cards size themselves in container-query units so the whole 3D scene is computed in CSS with no per-frame layout measurement. Loop and autoplay are deliberately out of v1.

## User Stories

1. As a product engineer, I want a carousel primitive in the design system, so that I can build media showcases without pulling in a third-party slider that ignores my tokens.
2. As a product engineer, I want a compound API (`Carousel` / `CarouselContent` / `CarouselItem` / `CarouselPrevious` / `CarouselNext` / `CarouselDots`), so that composition matches the shadcn carousel mental model my team already knows.
3. As a product engineer, I want a `useCarousel()` hook, so that I can build custom controls and status readouts against the carousel state.
4. As a designer, I want a `flat` staging that is a clean centered slider, so that I can use the carousel in dense dashboards without any 3D flourish.
5. As a designer, I want a `tilt` staging, so that I can add a restrained sense of depth to a feature row without a full stage.
6. As a designer, I want a `floor` staging where cards stand on a receding floor with contact shadows, so that a portfolio or gallery hero feels physical and premium.
7. As a designer, I want an `intensity` control (`subtle` / `standard` / `dramatic`), so that I can dial the rotation, depth, and blur multipliers to my brand's restraint level.
8. As a user, I want to drag the carousel with a pointer and have it settle with momentum, so that browsing feels tactile rather than stepped.
9. As a user, I want a flick past the ends to rubber-band and settle back in bounds, so that the carousel never scrolls into empty space.
10. As a keyboard user, I want arrow keys on the carousel to move between slides, so that I can browse without a pointer.
11. As a keyboard user, I want previous/next buttons that never steal focus, so that my focus stays where I put it while the slide changes.
12. As a keyboard user in RTL, I want arrow keys and previous/next controls to follow the writing direction, so that "next" always means the logical next slide.
13. As a screen-reader user, I want the carousel announced as a carousel with each slide labeled "N of M", so that I understand the structure and my position.
14. As a screen-reader user, I want control-driven slide changes announced politely, and drag not to spam announcements, so that updates are useful rather than noisy.
15. As a screen-reader and keyboard user, I want fully off-screen slides made inert, so that Tab never lands on a hidden card's nested link or button.
16. As a motion-sensitive user, I want reduced motion to flatten the 3D staging and replace spring animation with an instant jump and a gentle crossfade, so that browsing is comfortable.
17. As a developer, I want a controlled `index` / `defaultIndex` / `onIndexChange` API, so that I can drive the carousel from my own state and be notified once per settle.
18. As a developer, I want `onIndexChange` to fire exactly once when a slide settles, so that I do not get a burst of callbacks during drag or animation.
19. As a developer, I want position dots that reflect and set the active slide with `aria-current`, so that users get a compact overview and jump target.
20. As a developer, I want previous/next controls disabled at the bounds, so that users cannot page into nothing (no loop in v1).
21. As a developer, I want to pass an accessible name via `aria-label` / `aria-labelledby`, and be warned in development if I forget, so that the carousel is never an unlabeled region.
22. As a Next.js developer, I want server-rendered markup to show the correct resting slide and hydrate without warnings, so that the first paint is right and stable.
23. As a registry user, I want Carousel independently installable, so that installing it pulls Motion, the shared utilities, IconButton, and nothing else.
24. As a theming consumer, I want density, light, and dark mode reflected (including dark-mode contact-shadow colors), so that the carousel matches the rest of my app.
25. As a performance-conscious developer, I want depth blur capped and floor-only, and no `filter`/containment on the 3D track, so that the scene never triggers repaint storms or flattens.
26. As a component consumer, I want data attributes for every variant (`data-staging`, `data-intensity`, `data-reduced-motion`) and stable `data-slot` names, so that I can target states from my own CSS.
27. As a documentation reader, I want a spec, anatomy, API tables, accessibility notes, theming, recipes, and testing docs, so that I can adopt the carousel confidently.
28. As a Storybook user, I want stories for every staging, intensity, controlled usage, RTL, density, dark mode, reduced motion, nested focusables, and an Aurora-backed hero, so that I can review every state visually and with the a11y addon.
29. As a library maintainer, I want deterministic tests across pure math, rendered behavior, a11y, SSR, and motion seams, so that the carousel stays reliable as the library evolves.
30. As a designer, I want to compose the carousel with the existing AuroraBackground rather than a built-in backdrop, so that ambient effects stay a separate, reusable concern.

## Implementation Decisions

- New standalone compound component `Carousel` (slug `carousel`) in the media/showcase area of the inventory. Subcomponents: `Carousel` (root + context + engine), `CarouselContent` (viewport + track + per-item index context), `CarouselItem` (a slide), `CarouselPrevious` / `CarouselNext` (IconButton wrappers), `CarouselDots`. Public hook `useCarousel()`. No existing component is modified.
- Composition is wired through **React Context**, not CardScroller's `cloneElement`, because children are fully generic and the nav/dots subcomponents must work anywhere inside the root, and shadcn users expect a `useCarousel` hook.
- `CarouselProps`: `staging?: "flat" | "tilt" | "floor"` (default `"flat"`); `index?` / `defaultIndex?` (default `0`) / `onIndexChange?`; `drag?: boolean` (default `true`); `intensity?: "subtle" | "standard" | "dramatic"` (default `"standard"`, scaling rotate/depth/blur multipliers roughly ×0.6 / ×1 / ×1.4). Root carries `data-slot="carousel"`, `data-staging`, `data-intensity`, and `data-reduced-motion`, plus `role="region"` and `aria-roledescription="carousel"`. Consumers must supply `aria-label` or `aria-labelledby`; a development-only warning fires when neither is present.
- **`align` is center-only in v1** (open call resolved). The engine's continuous distance-to-center model is inherently center-anchored, and a `start` alignment would only be meaningful for `flat` while complicating the shared math, the dots mapping, and the resting-pose SSR. `flat` therefore centers the active card like the other stagings; no `align` prop is exposed. This keeps one coherent positioning model and reserves the prop name for a future minor release if a real start-anchored use case appears.
- **The offset engine**: a single `offset` MotionValue in float index units is the source of truth for position. It is mirrored to `--carousel-offset` on the root via a subscription (so SSR/first render can inline the resting integer index and the client updates the same property imperatively). Each `CarouselItem` sets `--carousel-item-index`; a shared CSS rule computes `--carousel-distance = item-index − offset`. All per-card transforms are CSS `calc()` of that distance; the far plateau is `clamp(-1.5, distance, 1.5)` and `abs(distance)` is expressed with `max(d, -d)`.
- **Layout is pure CSS with no per-frame measurement.** The root establishes a query container (`container-type: inline-size`) _outside_ the 3D context. Cards are absolutely centered and sized in container-query units (`--carousel-card-size`, e.g. `min(80cqw, …)`), so the center-to-center step is a resolvable CSS length and each card's horizontal position is `translateX(distance × step)`. Containment lives only on the root, never on the viewport or track, so `preserve-3d` is preserved. Drag still measures a pixel step from the rendered items to convert pointer pixels to index units.
- **DOM shape**: `div[data-slot=carousel]` (context, container, `--carousel-offset`) → `div[data-slot=carousel-viewport]` (clip + drag/keydown surface; for floor, `perspective` and a downward `perspective-origin` shared vanishing point on the viewport, never per-card) → `div[data-slot=carousel-track]` (`rotateX` for floor, `preserve-3d`) → `div[data-slot=carousel-item]*` (`--carousel-item-index`, `transform-origin: 50% 100%`, `backface-visibility: hidden`, `translateZ(0)` for Safari). Each item optionally renders an aria-hidden `div[data-slot=carousel-item-shadow]` (tilt/floor only) — a blurred ellipse that scales and fades with `abs(distance)`.
- **Drag** follows CardScroller's `DragSession` pattern: pointer capture after a ~10px threshold, click suppression on release, RTL sign from computed `direction`, rubber-band resistance (~0.35) past the ends. On release, pointer velocity is projected to an index target, rounded, clamped, and animated to with a spring (`type: "spring"`, roughly `stiffness: 90`, `damping: 18`). Buttons, dots, keyboard, and controlled syncing all funnel through one `scrollTo(index)` that uses the same spring, or `offset.jump(index)` under reduced motion.
- **Item indexing**: the root locates its `CarouselContent` child and derives `count = Children.count(content.children)` synchronously (deterministic, SSR-safe, Strict-Mode-safe, no registration store). `CarouselContent` provides each direct child its index via a lightweight item-index context. Only direct children of `CarouselContent` are supported slides; this constraint is documented.
- **Hydration and reduced motion** reuse the AuroraBackground pattern: a `useHasHydrated` gate means the OS reduced-motion preference is only trusted after hydration so the first client render matches the server; the tree is wrapped in `<MotionConfig>`. When reduced, the root gets `data-reduced-motion`, a CSS rule zeroes the rotate/depth/blur tokens and the floor `rotateX`, spring animations become instant jumps, and an active-slide change is communicated with an opacity crossfade rather than movement.
- **RTL**: a `--carousel-dir` token (default `1`, flipped to `-1` under `:dir(rtl)`) mirrors the horizontal math; drag sign and arrow-key mapping read the computed direction so "previous/next" stay logical while chevrons flip with `rtl:rotate-180`.
- **Accessibility (APG grouped carousel)**: root is `role="region"` + `aria-roledescription="carousel"`; each slide is `role="group"` + `aria-roledescription="slide"` + `aria-label="{i+1} of {count}"`. Previous/next never move focus. A polite live region announces control-driven changes and is silenced during drag. Fully out-of-view slides receive the `inert` attribute (guarding nested links/buttons), applied on settle only — never per animation frame — with the visible radius scaled by staging (flat 0, tilt 1, floor 2).
- **Styling**: new `--carousel-*` tokens are added to the package stylesheet following the `--timeline-*` precedent (perspective, perspective-origin-y, rotate-x, max-rotate-y, max-depth, min-scale, max-blur, gap from `--dt-density-gap`, card size in cqw, and light/dark contact-shadow colors). Calc-heavy per-item transform rules live in a small `[data-slot="carousel-item"]` block scoped by `[data-staging]`; everything else is Tailwind utilities in hand-rolled `Record<Variant, string>` maps merged with `cn()` (no `cva`, matching the repo). `intensity` writes inline CSS-var multipliers on the root following the CardScroller inline-var convention. Motion writes only `--carousel-offset`.
- **Exports**: all components, `useCarousel`, the `carousel*ClassNames()` recipe helpers, and all public types are exported from the package barrel after `card-stack`. The registry item (`registry:ui`) declares `registryDependencies: ["dethink-base", "icon-button"]`, `dependencies: ["motion"]`, and includes the component files plus the shared `cn` utility as `registry:lib`.

## Testing Decisions

- Tests target public behavior through the established seams — rendered markup and data attributes, jsdom interaction, string-level SSR output, and exported pure functions — never Motion internals or animation timing.
- **Pure math** (`carousel-utils`): snap-target selection from offset + projected velocity, rubber-band clamping past bounds, pixel-to-index conversion, and RTL sign, all covered exhaustively as pure functions.
- **Rendered behavior**: slot and data attributes per staging; controlled vs uncontrolled index; `onIndexChange` firing exactly once per settle; previous/next disabled at bounds; dots reflecting the active slide with `aria-current`; keyboard arrow navigation (LTR and RTL); the resting `--carousel-offset` present on first render; `flat` rendering no contact-shadow nodes while tilt/floor do; and `inert` applied to fully out-of-view slides.
- **Accessibility** (jest-axe): no violations for each staging; correct `aria-roledescription` on region and slides; "N of M" slide labels; and the development-only unlabeled warning.
- **SSR**: `renderToString` produces clean markup containing the resting pose and slot markers, deterministic across renders, and hydrates without mismatch warnings.
- **Motion**: reduced motion resolves to instant jumps, zeroed 3D tokens, and the `data-reduced-motion` attribute; the exported spring/config helpers behave as specified.
- **Storybook**: roughly twelve stories — Flat, Tilt, FloorGallery (hero), MarketingCards (nested focusables), GenericContent, Controlled, IntensityComparison, DarkMode, ReducedMotion, RTL, Density, and WithAuroraBackground — each with a `play` interaction test and the a11y addon clean.
- Prior art: the CardScroller suite (drag, controls, RTL, SSR) and the AuroraBackground suite (hydration gating, reduced motion, SSR determinism) are the templates.

## Out of Scope

- **Loop / infinite** paging — it conflicts with the continuous distance-to-center math and "N of M" labels; the API space is reserved for a future release.
- **Autoplay** — the APG pause-control requirements are a feature of their own and belong in a future `CarouselAutoplay`.
- **A built-in ambient/reactive backdrop** — compose with the existing `AuroraBackground` instead (a story demonstrates this).
- **`start` alignment** — center-only in v1 (see Implementation Decisions).
- **Vertical orientation, thumbnails/filmstrip navigation, and lightbox/zoom** — potential future work.
- **New design tokens beyond the `--carousel-*` set, or theme changes** — colors derive from existing semantic tokens plus the carousel-local shadow tokens.

## Further Notes

- This is the first component in the repository to introduce CSS 3D (`perspective` / `preserve-3d`). The known risks are documented and mitigated: animated `filter: blur()` is capped at ≤3px, floor-only, and dropped entirely at `intensity="subtle"`; no `filter` or `contain: paint`/containment is placed on the track (which would flatten the scene); floor staging uses `overflow-x: clip; overflow-y: visible` with generous block padding so cards translated toward the camera are not clipped; and `backface-visibility: hidden` + `translateZ(0)` guard Safari shimmer. A WebKit Playwright drag run is part of the final slice.
- Delivery is four tracer-bullet vertical slices: (1) flat core + skeleton (context, offset engine, drag, spring snap, buttons, keyboard, full a11y semantics, SSR/reduced-motion gating, barrel, registry, base stories, all test files started); (2) tilt staging (distance calc rules, intensity, reduced-motion flattening, stories); (3) floor scene (perspective viewport, rotateX track, contact shadows, depth blur, dark-mode shadow tokens, hero stories); (4) polish (RTL, density, inert edge cases, Playwright drag e2e, design-qa, docs finalization).
