# Identity And Labeling Primitives Spec

Status: Draft local spec for GitHub issue #314.

Parent PRD: https://github.com/parveshh/dethink-components/issues/313.

Issue breakdown: `docs/components/identity-labeling/issues.md`.

Package target: `@dethink/components`.

## Purpose

Identity and labeling primitives provide the shared contract for compact status,
identity, group identity, and standalone label surfaces before the individual
Badge, Avatar, AvatarGroup, and Label implementation issues begin.

The family is intentionally small. These components should compose with existing
primitives, registry items, and future data-display or form components without
owning workflows such as profile cards, selectors, filters, tooltips, form
validation, or realtime presence.

## Public API Direction

The approved v1 family is:

- `Badge`
- `Avatar`
- `AvatarGroup`
- `Label`

Exports should include each component, public prop types, constrained token
types, class-name helpers where consistent with existing primitives, and package
entry exports from `@dethink/components`.

All components should forward refs, accept native attributes appropriate to the
rendered element, merge `className` predictably with default classes, use static
Tailwind class maps, and expose stable data attributes such as `data-slot`,
`data-size`, `data-tone`, `data-variant`, `data-shape`, `data-state`,
`data-disabled`, `data-invalid`, and `data-motion` where relevant.

## Family Boundaries

- Badge owns compact, mostly static status and metadata labels.
- Avatar owns one visual identity surface for a user, team, organization, bot,
  or entity.
- AvatarGroup owns compact composition of multiple Avatar identities and their
  overflow summary.
- Label owns standalone native-first label rendering for controls outside or
  alongside FormField.
- FormField, FieldLabel, FieldControl, FieldDescription, and FieldError continue
  to own contextual form relationships, generated field IDs, description/error
  wiring, validation state propagation, and grouped form semantics.
- Button, IconButton, Link, Tooltip, HoverCard, Popover, DropdownMenu, Command,
  Table, DataTable, and future Tag/Chip components own their own interaction,
  disclosure, navigation, selection, and workflow behavior.

## Badge Contract

Badge should render a non-interactive inline element by default. Candidate
public tokens are:

- `variant`: `solid`, `soft`, `outline`, `subtle`
- `tone`: `neutral`, `primary`, `success`, `warning`, `destructive`, `info`
- `size`: density-friendly sizes for dense tables through roomy cards

Badge may support leading and trailing icon slots. Icons are decorative by
default when visible text already communicates meaning. Icon-only status badges
must use an explicit accessible label or a different component contract.

Badge must not own:

- Native button, link, checkbox, tab, menu item, toggle, or filter-pill
  semantics.
- Removable chip state or selection state.
- Motion behavior.
- Tooltip, HoverCard, Popover, or menu disclosure.
- Arbitrary user colors, random runtime colors, gradients, or status logic.

Interactive recipes should compose real Button, IconButton, or Link children or
adjacent controls so focus, activation, disabled, and accessible-name behavior
remain native.

## Avatar Contract

Avatar should render a stable square identity box with image, fallback initials,
or fallback icon content. Image and fallback states must preserve the same
dimensions to avoid layout shift in tables, menus, card headers, and chat
metadata.

Candidate public tokens are:

- `size`: `xs`, `sm`, `md`, `lg`, `xl`, `2xl`
- `shape`: `circle`, `rounded`, `square`
- `tone`: constrained token-backed fallback colors
- `ring`: constrained ring or border treatments for layered surfaces
- `motion`: `none`, `subtle`, `standard` if Motion-backed polish is approved in
  issue #317

Avatar image support should preserve native image behavior through props such as
`src`, `srcSet`, `sizes`, `alt`, `loading`, `decoding`, and safe image
attributes. Fallback initials should be explicit or generated by a deterministic
helper for common multi-word names without claiming full international name
parsing.

Avatar must not own:

- Image upload, crop, edit, compression, moderation, remote identity fetching,
  Gravatar, OAuth profile syncing, or permissions.
- Presence, online/offline state, notification count, collaboration cursors, or
  realtime subscriptions.
- User profile cards, account menus, person pickers, organization switchers, or
  selector workflows.
- Arbitrary user colors, random runtime colors, gradients, image filters, or
  brand artwork processing.
- Tooltip, HoverCard, Popover, or DropdownMenu dependencies.

## AvatarGroup Contract

AvatarGroup should compose Avatar instead of forking a separate identity visual
model. It should support visible members, maximum visible count, overflow count,
overlap spacing, group label, and member name metadata.

AvatarGroup overlap and spacing should use logical properties and documented
stacking order so LTR and RTL presentation are predictable. Overflow labels such
as `+3` must have a useful accessible name that explains the hidden member
count.

AvatarGroup must not own:

- Fetching, sorting, filtering, selecting, assigning, or editing members.
- Tooltip-dependent identity disclosure in v1.
- Hover-only member naming.
- Layout-changing expansion that pushes surrounding content in dense rows or
  toolbars.
- A duplicate Avatar API or visual treatment incompatible with Avatar.
- Popover, HoverCard, Tooltip, DropdownMenu, or people-picker workflows.

The base group in issue #318 should be useful without Motion. Issue #319 may add
optional reveal or spread polish only after the static accessible group contract
ships.

## Label Contract

Label should render a native `label` by default and support explicit `htmlFor`.
It should support required and optional markers, disabled and invalid visual
states, class merging, refs, custom attributes, and stable state data
attributes.

Label may align visually with FieldLabel and may later be composed by FieldLabel,
but it does not replace FormField's context-owned ID, description, error, or
state propagation contract.

Label must not own:

- Form validation, schema parsing, field arrays, dirty/touched state, async
  submit state, or form-library adapters.
- Automatic `required`, `disabled`, `readOnly`, or `aria-invalid` propagation to
  controls.
- `aria-describedby` or `aria-errormessage` wiring for descriptions and errors.
- Fieldset, legend, grouped control semantics, or generated IDs.
- Custom widget roles where native label semantics are available.

If `asChild` is considered, issue #316 must either preserve native label
semantics or document the exact accessibility tradeoff. The default contract is
native-first.

## Accessibility Invariants

- Use native HTML semantics before ARIA. Label renders a native `label` by
  default, and Avatar/AvatarGroup/Badge do not invent widget roles.
- Labels should be visible by default and explicitly associated with controls
  through `htmlFor` or valid native nesting.
- Identity surfaces must have reliable names. An Avatar that is the only
  identity surface needs a useful accessible name; an Avatar adjacent to visible
  identity text may be decorative with empty `alt` or `aria-hidden`.
- AvatarGroup must expose group and member identity information
  programmatically. Compact overlap cannot be the only representation of names.
- Disclosure cannot be hover-only. Any AvatarGroup reveal must also work on
  focus, and touch users need equivalent identity access through visible text,
  labels, descriptions, or explicit composition.
- Focus-visible styling must remain obvious for every interactive recipe,
  reveal trigger, composed button, composed link, and label-associated control.
- Status communication must not rely on color alone. Badge and Label examples
  for success, warning, destructive, info, required, optional, and invalid states
  need text, iconography, programmatic state, or other non-color signals.
- Motion and animation must never be the only way to communicate identity,
  status, validation, or disclosure state.

## Motion Decisions

Badge and Label must remain dependency-free and must not import Motion for v1.

Avatar and AvatarGroup may use Motion only for non-essential polish, and only in
the implementation issues where the dependency boundary is explicit:

- Avatar issue #317 may use Motion for subtle hover/focus image or fallback
  polish if CSS `motion-safe` transitions are not enough.
- AvatarGroup issue #319 may use Motion for overlap spread or name reveal after
  the base group from issue #318 is already accessible without animation.
- Motion effects should animate transform and opacity, not layout-affecting
  dimensions.
- Base transform state should be explicit, for example an identity transform, so
  hover/focus transforms do not create surprising stacking or paint behavior.
- Reduced motion must disable or replace transform-heavy behavior. The reduced
  presentation must remain stable and fully informative.
- Motion imports should be isolated to Motion-enabled files or variants so
  static Badge, Label, Avatar, and base AvatarGroup registry installs do not
  inherit unnecessary dependencies.

Context7 resolved Motion documentation to `/websites/motion_dev`; relevant
Motion React docs support gesture props such as `whileHover`, `whileFocus`, and
`whileTap`, plus reduced-motion handling. Implementation agents should recheck
current docs before writing Motion code if API details matter.

## Styling And Theming

- Use Tailwind CSS v4 utilities, semantic tokens, CSS variables, static class
  maps, and the shared class-name merge helper.
- Avoid hard-coded brand colors and runtime-generated Tailwind class names.
- Support light mode, dark mode, high contrast, density, RTL, and responsive
  wrapping through tokens, data attributes, and logical properties.
- Prefer `data-density` and selector-based density behavior for core component
  spacing. Do not rely on newly available container style queries for required
  behavior unless a fallback is documented.
- Use visible text, icons, or programmatic state alongside tone classes for
  critical statuses.
- Components copied through the registry must remain portable and must not
  depend on hidden global styles beyond documented base setup.

## Registry, Package, And Dependency Strategy

Each primitive should have a focused shadcn-compatible registry item when its
dependency boundary differs:

- `badge`: depends on base utilities only; no runtime dependency.
- `label`: depends on base utilities only; no runtime dependency.
- `avatar`: depends on base utilities only by default. If optional Motion
  behavior ships, isolate it so the static registry item remains dependency-free
  or make the Motion dependency explicit in a separate file/item.
- `avatar-group`: depends on Avatar and base utilities. It should not pull
  Motion, Tooltip, HoverCard, Popover, or DropdownMenu into the base install.
- Optional AvatarGroup reveal/polish should declare Motion only in the registry
  item or recipe that actually imports `motion/react`.

Package exports should expose every public component and prop/token type from
`@dethink/components`. Registry metadata must accurately list files,
dependencies, devDependencies, registry dependencies, CSS variable expectations,
and any package export changes.

Dependency boundaries matter because consumers should be able to install Badge
or Label without paying for Avatar, AvatarGroup, or Motion, and install static
Avatar/AvatarGroup without disclosure dependencies they did not choose.

## Testing Seams

- Render tests for native output, variants, sizes, tones, shapes, states,
  fallback rendering, overflow counts, markers, custom attributes, refs,
  `className` merging, and stable data attributes.
- Accessibility tests for axe smoke, native label/control association, reliable
  identity names, decorative avatar patterns, AvatarGroup member exposure,
  no hover-only disclosure, visible focus, and no color-only status examples.
- Motion tests for Avatar and AvatarGroup where Motion is implemented:
  `motion="none"`, enabled presets, focus and hover triggers, reduced-motion
  behavior, and transform/opacity-only animation targets where practical.
- SSR tests for server rendering and hydration without browser-only access,
  generated ID mismatches, random fallback colors, or non-deterministic initials.
- Type tests for constrained variants, tones, sizes, shapes, marker options,
  motion presets, and unsupported values where practical.
- Storybook and visual coverage for light, dark, density, high contrast, RTL,
  narrow containers, dense table cells, card headers, AI/chat metadata,
  image/fallback/avatar-group overflow states, and label-associated native
  controls.
- Registry and playground smoke checks for every item, dependency metadata,
  copied-source portability, package exports, CSS variable expectations, and
  clean consumer installation.

## Out Of Scope

- Implementing component source code in issue #314.
- Replacing FormField or FieldLabel.
- Input widgets, validation engines, form-library adapters, or fieldset/legend
  group primitives.
- TagInput, Chip, selectable filters, tabs, menu items, segmented controls, and
  command/list option selection.
- Presence, profile cards, people pickers, organization switchers, account
  menus, Tooltip, HoverCard, Popover, and DropdownMenu workflows.
- Avatar image upload, crop, editing, moderation, remote fetching, or provider
  integration.
- Mandatory Motion for static primitives or any Motion behavior for Badge and
  Label.
- CSS-in-JS, styled-components, Emotion, arbitrary `sx` props, random colors,
  arbitrary color strings, runtime class generation, and undocumented global CSS.

## Definition Of Done For #314

- Local contract docs reference parent PRD #313.
- Component boundaries define what Badge, Avatar, AvatarGroup, and Label own and
  must not own.
- Accessibility invariants are explicit for native labels, identity names,
  hover disclosure, focus, and color-independent status communication.
- Motion decisions are explicit for Avatar and AvatarGroup, including reduced
  motion and dependency isolation.
- Registry, package, export, and dependency-boundary strategy is documented.
- Approved implementation issues #315 through #320 and dependency order are
  mapped for follow-on agents.
